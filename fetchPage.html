Snap Fetch

How to use fetch() instead of Axios (or other similar libraries) without losing out on any of Axios's distinguishing features.

We will start with the following piece of boilerplate - everything discussed below will add onto this.

//# selectAllButton
class HttpError extends Error {
  constructor(request, response) {
    super(
      `Request failed with status ${response.status} ${response.statusText}: ` +
      `${request.method} ${request.url}.`,
    );
    this.request = request;
    this.response = response;
  }
}

async function sendRequest(url_, opts = {}) {
  const {
    body: body_ = undefined,
    jsonBody = undefined,
    headers: headers_ = {},
    queryParams = undefined,
    ...etc
  } = opts;

  // Add `queryParams` to the URL
  const url = new URL(url_);
  for (const [key, value] of new URLSearchParams(queryParams)) {
    url.searchParams.append(key, value);
  }

  // JSON-encode the `jsonBody`
  const body = jsonBody === undefined ? body_ : JSON.stringify(jsonBody);

  // Add a default application/json header if `jsonBody` is being used.
  const headers = new Headers(headers_);
  if (jsonBody !== undefined && !headers.has('Content-Type')) {
    headers.set('Content-Type', 'application/json')
  }

  // Send the request
  const request = new Request(url, { body, headers, ...etc });
  const response = await fetch(request);
  if (!response.ok) {
    throw new HttpError(request, response);
  }

  return response;
}

// const response = await sendRequest('https://jsonplaceholder.typicode.com/posts', {
//   method: 'POST',
//   jsonBody: { title: 'foo', body: 'bar', userId: 1 },
// })
//   .then(resp => resp.json());

// Query parameters example:
// const response = await sendRequest('https://jsonplaceholder.typicode.com/comments', {
//   queryParams: { postId: 1 },
// })
//   .then(resp => resp.json());

This code does a few useful things for us:

  1. It throws an instance of HttpError on bad HTTP codes.
  2. It allows us to provide a jsonBody parameter, which it will automatically JSON-stringify and use as the request body, and set the appropriate Content-Type header to go with it.
  3. It allows us to provide queryParams, which it'll auto-attach to whatever URL we provide.

This is a fairly solid core to get you started. What follows are various features Axios provides, and how you can get those same features with native fetch().

Create Customized Instances

Axios lets you create new instances of the Axios class with certain configuration pre-applied, such as automatically providing auth headers or supplying a base URL.

I would argue the native fetch() API handles this even better than Axios. If you want a customized fetch(), you just wrap it in your own custom function, that's it. Easy to understand, and no special explicit support is required.

// By the way, this jsonplaceholder.typicode.com website is pretty awesome.
// It provides a mock REST API anyone can use.

async function jsonPlaceholderFetch(path, { headers: headers_ = {}, ...etc } = {}) {
  // Set a base URL
  const url = new URL(path, 'https://jsonplaceholder.typicode.com');

  // Provide auth headers
  const headers = new Headers(headers_);
  const encodedCreds = btoa('dummyUsername:dummyPassword');
  headers.set('Authorization', `Basic ${encodedCreds}`);

  return await sendRequest(url, { headers, ...etc });
}

// Example usage:
// const response = await jsonPlaceholderFetch('/todos/1')
//   .then(resp => resp.json());

Interceptors

This, too, is arguably handled better with fetch() than Axios. To intercept requests, just edit your wrapper functions to include your interception logic. For example, if you want to cause any 401 error to redirect the end-user to the login screen, simply add the code to the appropriate wrapper function.

In this case, we'll add it to our jsonPlaceholderFetch() function defined earlier. (We'll also remove the basic-auth header logic and instead assume cookies are being used to authenticate the request - those cookies may expire and cause you to become logged out).

async function jsonPlaceholderFetch(path, opts = {}) {
  // Set a base URL
  const url = new URL(path, 'https://jsonplaceholder.typicode.com');

  try {
    return await sendRequest(url, opts);
  } catch (error) {
    if (error instanceof HttpError && error.response.status === 401) {
      // The user is logged out, redirect them to the login screen.
      window.location.href = '/login';
    } else {
      throw error;
    }
  }
}

Request Timeouts

If you want to abort a request after, say, 10 seconds, you can use fetch()'s native abort system as follows:

const response = await sendRequest('https://jsonplaceholder.typicode.com/todos/1', {
  signal: AbortSignal.timeout(10_000),
})
  .then(resp => resp.json());

Automatically JSON-Parsing Results

Yes, Axios can automatically JSON-parse your results.

But Axios's implementation for this is actually quite poor. They try to blindly JSON-parse all response bodies, regardless of what responseType says, and if they're successful, they will return the parsed version, which causes real issues such as lost precision in numbers that were never meant to be interpreted as JSON.

A better implementation would be to only JSON-parse when the Content-Type header contains application/json. You could choose to provide automatic parsing for other Content-Types as well. I'm personally not a fan of this approach though. For one, on success responses, that Content-Type header is typically redundant information - your client code is already hard-coded to expect JSON, there's no point in letting the server decide for you how to try to parse the response when there's only one option your client accepts - JSON (same is true for other content types).

Parsing Content-Type headers can also be finicky. The server may return Content-Type: application/json today, then later switch it to Content-Type: APPLICATION/JSON, or Content-Type: application/json; charset=utf-8 both of which should behave the same way. They may even change their header to something like Content-Type: application/fhir+json, saying "this isn't any JSON, but fhir-standard-compatible JSON" (FHIR being a special patient-data format - there's many such context-specific JSON content-types).

Tracking Upload Progress

The one thing that fetch() does not support, that XMLHTTPRequest does support (and Axios by extension, since it is built on XMLHTTPRequest) is the ability to track the progress of a file upload.

So, if you need this and aren't using Axios, just use XMLHTTPRequest. Yes, it's ugly, but you can clean it up with a helper function.

//# selectAllButton
async function uploadFile(url, opts) {
  const {
    method,
    file,
    headers: headers_ = undefined,
    onProgress = undefined,
  } = opts;

  return await new Promise((resolve, reject) => {
    const xhr = new XMLHttpRequest();
    const formData = new FormData();
    formData.append('file', file);

    xhr.upload.onprogress = event => {
      if (event.lengthComputable) {
        // Provides the caller with progress events.
        // This can be displayed to the end-user with
        // `loaded / total` amount of a progress bar filled up.
        onProgress?.({ loaded: event.loaded, total: event.total })
      }
    };

    xhr.onload = () => {
      if (xhr.status >= 200 && xhr.status < 300) {
        resolve(xhr.responseText);
      } else {
        const error = new Error(`Upload failed with status: ${xhr.status}`);
        error.status = xhr.status;
        reject(error);
      }
    };

    xhr.addEventListener('error', () => {
      reject(new Error('A network error occurred.'));
    });

    xhr.open(method, url, true);

    const headers = new Headers(headers_);
    for (const [key, value] of headers) {
      xhr.setRequestHeader(key, value);
    }

    xhr.send(formData);
  });
}

Support for streaming requests to the server may be supported in the future, which would let you track how much has been sent up, which can be used to make a progress bar.

Improved Error Handling

When using either Axios or the sendRequest() implementation on the server-side, I find the uncaught error messages to be sub-par. In both cases, they'll log out a large volume of data, much of which is useless when trying to understand what went wrong. I would recommend beefing up the HttpError class to provide relevant information in the error message itself, then hiding the other properties so they don't get logged out, as follows:

//# selectAllButton
class HttpError extends Error {
  constructor(request, response, responseBody) {
    super([
      `Request failed with status ${response.status} ${response.statusText}.`,
      `Endpoint: ${request.method} ${request.url}`,
      '--- Response body ---',
      (responseBody.length > 1000 ? responseBody.slice(0, 1000) + '…' : responseBody),
      '--- Request headers ---',
      ...[...request.headers].map(([key, value]) => key + ': ' + value),
      '--- Response headers ---',
      ...[...response.headers].map(([key, value]) => key + ': ' + value),
      '------------------------',
    ].join('\n'));

    // Ensuring these properties aren't enumerable.
    // Node won't log out non-enumerable properties, and these properties can
    // create quite a lot of noise in the logs when logged out.
    Object.defineProperty(this, 'request', { value: request, enumerable: false });
    Object.defineProperty(this, 'response', { value: response, enumerable: false });
    Object.defineProperty(this, 'responseBody', { value: responseBody, enumerable: false });
  }

  static async create(request, response) {
    return new HttpError(request, response, await response.text());
  }
}

Make sure you call await HttpError.create() instead of new HttpError() to create instances.

Design Notes

View

Why do I keep doing .then(resp => resp.json())? Why not const parsedResponse = await resp.json()?

Why needlessly introduce an extra variable to the function's scope (the resp variable), when its only use is for the very next line (to do await resp.json())?

Many JavaScript developers, myself included, have been craving for the introduction of a pipeline operator. We don't have it yet, but the promise API does provide methods that are very pipeline-like - doing .then(...) isn't that different from adding a step to a pipeline.

Yes, await syntax is newer and very useful, but its existence shouldn't cause us to boycott all uses of .then() and .catch(), they have their uses too.

Why are you throwing on bad status codes? Isn't it bad to use errors for control flow?

No. Idiomatic JavaScript says that you throw an error if the operation you're trying to perform failed. JSON.parse(), for example, throws a SyntaxError when you supply bad JSON. If, on the application end, it's expected that you may be supplying bad JSON, you may be required to catch that SyntaxError and handle it, making error handling be part of your control flow, and that's ok. Good even. The alternative would be for JSON.parse() to return the syntax error information and rely on all callers to manually throw it if bad JSON was unexpected, which makes for an uglier API to use, and forgetting to throw the errors can make for hard-to-debug issues.

Almost all built in and third-party APIs follow this approach, of throwing on failure. fetch() itself still somewhat follows this philosophy. If you're completely disconnected from the internet, it will throw an error. Network instability should be expected in any given webpage, so you'll need to be checking for this and handling it appropriately, making these errors part of your normal control flow.

A common counter argument is that a bad status code isn't a failure, fetch() is just transmitting the response message to you, good or bad. To which I would argue Of course it is an error. If you request a JSON file and the server responded with 404, then your request for that file has failed. fetch() speaks and understands many aspects of the HTTP standard. Status codes, such as 404, are defined by the HTTP standard as being error codes. There's no reason fetch() shouldn't interpret this as an error and throw it. This is an unfortunate flaw in fetch()'s design that we don't need to try and excuse away.

In the end, it's simply more convenient to let your application do all error handling in the catch block, as opposed to handling network errors in a catch block and other failures outside.

What's with your variable names with trailing underscores, such as headers_?

It's a loose combination of different ideas that's turned into a habit I've picked up.

In Python's PEP 8's style guide, they recommend putting a trailing underscore on a variable name if you want to use a name that conflicts with a built-in name or keyword, such as naming a variable class_ instead of class, since class is a reserved keyword. I've taken some creative liberty with this guideline and have started using trailing underscores to avoid any kind of name conflict, not just conflicts with built-in names.

Functional languages often allow the apostrophe character in names, such as x', which reads as "x prime". If you want to create a new x variable that's been modified, you'd name your modified version x' instead of x (since you're typically not allowed to overwrite the existing variable). JavaScript doesn't let you use apostrophes in variable names, but I still often try to avoid reassigning variables, preferring instead to create new variables, where the less-used one would be named with a trailing underscore to distinguish it.

Put together, I've grown into a pattern of naming variables holding unnormalized values with a trailing underscore, then once I've normalized them the way I like, I store that in a variable without the trailing underscore. Of course, if you don't like it, feel free to change it up to your preferences. But I do think it would be cool if this became a pattern that was more widely adopted.
